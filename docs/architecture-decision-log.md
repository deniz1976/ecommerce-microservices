# Architecture Decision Log

This document records important decisions and why we made them.

## Decision 1: Use .NET 10

Decision:

```text
Use .NET 10 for all services.
```

Reason:

- User requested modern .NET.
- Local SDK `10.0.301` works.
- Project builds successfully with `net10.0`.

Tradeoff:

- Some libraries may still be catching up.
- We need to watch package compatibility.

## Decision 2: Use Microservices

Decision:

```text
Split system into multiple services by business capability.
```

Reason:

- E-commerce has clear boundaries.
- Catalog, Basket, Ordering, Inventory, Payment, Shipping, Notification, and Identity can evolve separately.

Tradeoff:

- More moving parts.
- More documentation and operational complexity.

## Decision 3: Database Per Service

Decision:

```text
Each service owns its own PostgreSQL database.
```

Reason:

- Strong service ownership.
- Avoid shared database coupling.
- Aligns with microservice best practice.

Tradeoff:

- Cross-service joins are not allowed.
- Reporting/read models may be needed later.

## Decision 4: Use Neon PostgreSQL

Decision:

```text
Use Neon for PostgreSQL databases.
```

Reason:

- Managed PostgreSQL.
- Easy to create multiple databases.
- Good fit for development and early production experiments.

Tradeoff:

- Need to manage connection limits and pooling.
- Need careful connection string management.

## Decision 5: Use RabbitMQ Through CloudAMQP

Decision:

```text
Use CloudAMQP-hosted RabbitMQ.
```

Reason:

- Managed broker.
- No need to operate RabbitMQ locally for prod-like messaging.
- RabbitMQ fits command/event workflow well.

Tradeoff:

- Requires network dependency.
- Runtime needs valid secrets.

## Decision 6: Use MassTransit

Decision:

```text
Use MassTransit on top of RabbitMQ.
```

Reason:

- Strong .NET integration.
- Typed consumers.
- EF inbox/outbox support.
- Reduces manual broker plumbing.

Tradeoff:

- Runtime topology is generated by conventions.
- Developers need to learn MassTransit concepts.

## Decision 7: Use Transactional Outbox

Decision:

```text
Use EF Core outbox per publishing service.
```

Reason:

- Prevents losing messages when DB save succeeds but broker publish fails.
- Keeps outgoing messages inside service transaction boundary.

Tradeoff:

- Adds infrastructure tables.
- Adds operational need to monitor outbox backlog.

## Decision 8: Keep Inbox/Outbox Inside Each Service DB

Decision:

```text
Do not create separate inbox/outbox service or database.
```

Reason:

- Inbox/outbox state belongs to the service transaction.
- Avoid central bottleneck.
- Avoid distributed transaction complexity.

Tradeoff:

- Each DB contains infrastructure tables.
- Each service needs its own migration and monitoring.

## Decision 9: Use Saga Worker for Order Workflow

Decision:

```text
Use separate Ordering Saga Worker.
```

Reason:

- Order workflow spans Inventory, Payment, and Shipping.
- Durable workflow state is needed.
- Compensation logic should be centralized for the order process.

Tradeoff:

- More moving parts.
- Saga state and retries need careful monitoring.

## Decision 10: Use Redis for Active Basket

Decision:

```text
Store active basket state in Redis.
```

Reason:

- Basket is temporary.
- Basket changes frequently.
- Redis is fast for session-like state.

Tradeoff:

- Need managed Redis for production.
- Local Redis is only development-friendly.

## Decision 11: Use PostgreSQL for Basket History

Decision:

```text
Store checkout snapshots in PostgreSQL.
```

Reason:

- Checkout history is durable business data.
- It should survive Redis eviction/restart.

Tradeoff:

- Active and historical basket data are split across Redis and PostgreSQL.

## Decision 12: Use Ocelot API Gateway

Decision:

```text
Use Ocelot as gateway.
```

Reason:

- Simple .NET gateway.
- Good enough for routing in this phase.
- Keeps clients away from individual service ports.

Tradeoff:

- Advanced gateway features may need extra work.
- Alternatives like YARP may be considered later.

## Decision 13: Add SignalR Notifications

Decision:

```text
Use SignalR for realtime notifications.
```

Reason:

- .NET-native realtime communication.
- Good fit for customer notification updates.

Tradeoff:

- Scale-out later needs backplane or managed SignalR.

## Decision 14: Keep Secrets Out of Tracked Files

Decision:

```text
Do not commit real connection strings or passwords.
```

Reason:

- Git history is hard to clean.
- Secrets in source control are a security risk.
- Runtime env vars are safer.

Tradeoff:

- Local startup requires env setup.
- More scripts are needed to check env readiness.

## Decision 15: Add Documentation Early

Decision:

```text
Create detailed docs before the project becomes too large to explain.
```

Reason:

- The system already has many services and patterns.
- Documentation helps learning and maintenance.

Tradeoff:

- Docs must be kept up to date.
